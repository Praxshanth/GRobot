## Finished (what exists and works today)

**Platform foundation (M0).** uv + pnpm monorepo, FastAPI API (public app and a separate internal-only app), Next.js app, Celery worker skeleton, Docker Compose (Postgres + pgvector, Redis, MinIO, Mailpit, optional Authentik), structured logging, OTel wiring, problem+json errors, import-boundary test (vendor AI frameworks only inside `adapters/`).

**Identity, tenancy and security (M1).**
- Multi-tenancy from day one: server-derived `TenantContext`, tenant-scoped repositories, PostgreSQL row-level security on every tenant table (app role cannot bypass it), cross-tenant suites returning 404, append-only audit log, transactional outbox.
- Authentication by Better Auth (email/password, email verification and reset) issuing JWTs the API verifies via JWKS; same-origin proxy with CSRF origin check; API accepts bearer tokens only.
- Authorization by Casbin only (hierarchical roles, single `require()` enforcement point, escalation and last-owner guards); the UI receives server-decided permissions and never re-implements them.
- Organization onboarding, members, roles, invitations (hashed tokens, single use), workspaces, keyset pagination.
- **Per-organization SSO, OIDC and SAML 2.0:** GRobot owns the model and syncs it into Better Auth's SSO plugin behind a gateway/adapter (no custom protocol code); DNS-verified exact domains (one org per domain), JIT provisioning capped below admin, protocol-strict login decisions, enforce-SSO with a lockout guard, hardened SAML (signed assertions, `InResponseTo`/replay protection, strong-algorithm allow-list that closes a plugin gap, DTD-free metadata parsing).
- Hardening: client secrets AES-GCM encrypted in GRobot and again inside the auth schema; dual-key rotation with `make rotate-secrets`; SSRF-safe fetcher and an egress guard for outbound IdP calls (connect-time address checks); internal routes on separate unpublished listeners with HMAC-signed calls; trusted-proxy client IP; per-IP/per-user/per-write API rate limits and a per-client discovery limiter; plugin management endpoints closed.
- Dashboard shell: navigation (future modules labeled "Soon", never faked), org switcher, Overview, Team, Settings (General, Model providers, Single sign-on), demo-data banner.

**Agents (M2).** Agent + immutable version tables (`agent_version` is INSERT/SELECT only for the app role), strictly validated config blocks (model, handoff, lead capture, widget, allowed origins), template registry with the Construction Lead Agent, draft/published/paused lifecycle with publish-readiness checks, "unpublished changes" tracking, model-provider credentials (encrypted, write-only, row-bound), agents UI (list, create from template, Overview, Instructions & model, Lead capture, Handoff, Deployment with versions).

**Knowledge (M3).** Knowledge bases per workspace with a fixed embedding model; sources are uploaded files (PDF, DOCX, TXT, Markdown; originals in S3/MinIO) or web pages (single page or same-host crawl up to depth 2 / 25 pages, robots.txt honored, SSRF-safe at add time and at connect time). Validation by content (magic bytes must match the extension), decompression-bomb limits, size caps, per-KB duplicate rejection by checksum/address. Heading-aware token-bounded chunking; embeddings via OpenAI/OpenRouter/OpenAI-compatible providers (through the SSRF-safe fetcher) or a built-in keyless hashing embedder (labeled keyword-level); `vector(1536)` + HNSW on the chunk row. Celery ingestion with `job_run` idempotency, a per-source `generation` that makes stale/duplicate deliveries no-ops, one-transaction index replacement, retry with backoff for transient failures, a usage ledger (append-only), and a celery-beat sweeper that re-queues sources lost between commit and enqueue (or fails them visibly after 5 attempts) through a single SECURITY DEFINER function. Knowledge UI: list/create, sources with live status, upload (multi-file), add URL (depth/pages), retry/re-index/remove, embedding change + re-index all, chunk viewer, per-agent attachment tab, demo seed (Summit Ridge documents). See `docs/knowledge.md`.

**RAG runtime + playground (M4).** `NativeRuntime` (guardrails → deterministic service-area check → query condensation → tenant-scoped pgvector retrieval → grounding floor → generation with fallback model), trust-segmented prompts with escaped delimiters, no model-callable tools, providers for OpenAI/OpenRouter/OpenAI-compatible/Anthropic/Google over streaming SSE with normalized usage and classified errors, a built-in keyless extractive answerer, retrieval records with snapshotted hits, metered chat/embedding usage, and the agent **Testing** tab: streamed chat on the working copy with citations and a "Why this answer?" inspector (scores, used/cited passages, rewritten query, service-area verdict, fallback notice). See `docs/ai-runtime.md`.

**Conversations (M5).** Channel-agnostic `ConversationService` (visitor, conversation, participant, message tables; per-conversation gap-free sequence numbers allocated under the row lock; append-only transcripts for the application role; failed turns stored but not replayed; history windowing; conversation/message usage metering). The playground now persists every test, keeps history server-side (a client can no longer forge earlier turns), and resumes previous tests. Conversations nav/list (search, agent/channel filters, sort, keyset pagination) and transcript detail with per-answer sources inspector, token usage, latency and admin delete. See `docs/ai-runtime.md`.

**Website widget (M6).** Public visitor API (`/public/v1/agents/{id}/…`: config, start conversation, SSE messages, history) with per-agent origin allowlists and CORS, HMAC tokens bound to agent/conversation/visitor/origin with sliding expiry, hashed anonymous visitor ids, per-IP and per-conversation rate limits with proxy-aware client IPs, a pre-tenant read-only lookup of exactly one published agent, visitors served from the *published snapshot*, no internal data or model errors in payloads, citation markers stripped from streams. `apps/widget`: Preact + Shadow DOM bundle (11 KB gzipped) with isolation from hostile host CSS, text-only rendering (no HTML path), streaming, typing state, retries, offline handling, restore after reload, consent gate, mobile full-screen, keyboard/ARIA basics. Deployment tab install snippet and a demo host page. See `docs/widget.md`.

**Lead capture (M7).** `lead` (one per conversation, validated fields, platform-computed service-area verdict, `incomplete`→`new` on first contact detail, staff statuses and notes, test leads kept apart), conversational capture driven by the platform (intent detection, strict rule-based extraction, optional model JSON extraction for free-text fields, template questions limited to two per reply and two unanswered in a row, one-time confirmation), widget contact-form fallback, per-agent out-of-area policy (inform / collect anyway / handoff), durable per-recipient notifications (agent emails + organization webhooks) delivered by the worker with retries and a lost-job sweeper, HMAC-signed SSRF-safe webhooks with once-shown encrypted secrets, and the Leads list/detail UI, webhook settings and notification-email field. The model cannot call tools or choose where data goes. See `docs/leads.md`.

**Human handoff (M8).** Per-conversation state machine (`AI_ACTIVE → HANDOFF_REQUESTED → HUMAN_ACTIVE → RESOLVED → AI_RESUMED`) as one declared transition table enforced under the row lock; triggers evaluated in code (visitor asks for a person, sensitive keywords, unanswerable, low confidence, out of area); the agent never speaks while a teammate is active, including answers that finish after a takeover (dropped at store time); two operators racing yields exactly one winner; manager override; operator replies reach the visitor's open chat in about a second over a server-sent-event stream with state banners and reload restore; the dashboard Inbox (waiting / mine / open / resolved, live polling, thread with take over / reply / resolve / hand back) with a navigation badge; durable email paging with retries and a lost-job sweeper. See `docs/handoff.md`.

**Dashboard and analytics (M9).** Read-only analytics over existing rows (no new tables, no rollup jobs): headline numbers with change against the previous period, a zero-filled daily series, channel / reply-outcome / lead-status breakdowns, per-agent table, top and unanswered questions, and a usage-and-cost report split into conversations, testing and indexing. Time-zone aware windows (DST-correct), agent/workspace/test filters, `analytics:read` for agent operators and up, estimated cost from a reviewed price table that never guesses an unlisted model. Overview shows the last 30 days; Analytics page and a per-agent Analytics tab share one view with accessible SVG charts and table alternatives. See `docs/analytics.md`.

**Developer experience.** `make up / api / web / worker / check / e2e / seed / reset-db / rotate-secrets / resync-sso`; idempotent flagged demo seed (Summit Ridge Remodeling); clean-room CI verification; Playwright browser tests.

**Known small gaps (not scheduled to a milestone yet):** operator replies are delivered by polling (1 s while a person is involved), which is fine for hundreds of open chats but would be replaced by push (Redis pub/sub or LISTEN/NOTIFY) at larger scale; there is no typing indicator, read receipt, canned replies, internal notes between teammates, or business-hours routing; the agent's answer can be briefly visible to a visitor if a teammate takes over mid-stream (it is then not stored); handoff pages go to email only (no Slack/SMS); `status` (`open`/`closed`) on conversations is still unused; lead intent and service vocabulary are tuned for the construction vertical (other industries extend `SERVICES`/intent patterns per template); the conversational extractor reads English only; leads cannot yet be assigned to a teammate or exported (the `assigned_to` column exists, the UI/API do not); no lead de-duplication *across* conversations (the same person chatting twice is two leads); only `lead.created` events exist for webhooks; the one-answer-at-a-time guard is per API process (a multi-process deployment needs a shared lock); the widget has no file upload, rich cards or typing indicator for human agents (M8); public-API rate limits are per-IP so many visitors behind one NAT share a budget; the widget is not yet served from a CDN with versioned URLs (`/widget.js` always latest); conversations have no retention/auto-delete policy or PII redaction yet (M14/M15); transcript export is not built; `status` is always `open` until M8 introduces closing/resolution; the built-in answerer is extractive and basic (real models are the production path); HNSW recall at large scale with selective tenant filters is unmeasured (the retriever sets `hnsw.iterative_scan`; load test in M14); hybrid/BM25 search and reranking are deferred; the model cannot call tools yet (M12/M13); scanned/image-only PDFs are rejected with a clear message (no OCR); DOCX images and embedded objects are ignored; embeddings need an OpenAI-compatible `/embeddings` endpoint (Google and Anthropic embedding APIs are not wired) at width 1536; chunk token counts are an estimate, not a model tokenizer; crawler ignores sitemaps and JavaScript-rendered pages; no per-organization storage quota (M15) or malware scanning of uploads yet (M14); OIDC `private_key_jwt`; SAML certificate-expiry alerting and metadata auto-refresh; SCIM and IdP group→role mapping; SAML encrypted assertions, single logout, IdP-initiated SSO (intentionally unsupported); GitHub Actions has never executed the workflow.

**Carried into M14 (partly done early):** key rotation and rate limiting are already implemented; remaining are load/soak tests, threat-model review, dependency/container scanning, backup/restore drill, retention/deletion, production compose/Helm, OpenAPI + SDK generation. RLS is already enforced at runtime (the application role is not the table owner); M14 is the production/ops review of it, not its introduction.

## Open decisions (defaults will be used unless you object)
1. **Auth:** Better Auth is the authority, built-in accounts + OIDC SSO; Authentik optional (ADR 0004, revised).
2. **SAML** shipped alongside OIDC (same model, sync and safeguards; see ADR 0004); SCIM user provisioning and IdP group→role mapping are later.
3. **Native runtime first;** Langflow is dropped (ADR 0007); M13.3 shipped a GRobot-native runtime behind `AgentWorkflowRuntime` (ADR 0040; LangGraph evaluated, not adopted, ADR 0014 updated); deterministic automation is GRobot Flow (ADR 0010).
4. **Widget UI in Preact** (small bundle) rather than React.
5. **Default LLM for dev/demo:** provider chosen by env; tests use a deterministic fake provider.
6. **Name `GRobot`** is a working title (package prefix `grobot_`).

## M13 — Agentic Execution Foundation (GRobot Cortex + Approvals)
Umbrella milestone with four independently reviewed sub-milestones; each preserves earlier architecture, passes the complete suite, gets its own local commit, stops for review and is tagged `m13.N-accepted` only after review. Scope and rationale: `docs/m13-scope.md`. ### M13.1 — Tool Approvals  ☑ (accepted)
Design: ADR 0033 (engine independent of Cortex), 0034 (exact-action binding, single use, state machine), 0035 (policy and separation of duties), 0036 (content approval vs tool-call approval); `docs/approvals.md`. Commit `6c23153` on `develop`; tag `m13.1-accepted`.
**Goal:** a HIGH-risk (or `ALWAYS`) tool call no longer dead-ends in `approval_required`; it becomes a durable, exact, single-use approval lifecycle that Flow, MCP and API callers share, and a future Cortex will consume.
**Built:**
- **Engine** (`grobot_core.approvals`, imports no agent runtime, gateway, Flow, MCP, connector or Vault): canonical JSON (`canonical.py`), action envelope and SHA-256 fingerprint (`fingerprint.py`), state machine (`states.py`), policy and `may_decide` (`policy.py`), persistence/claim/sweep (`engine.py`), bounded-label metrics.
- **Schema** (migration `f8b6d03e5a57`): `pending_action` (requester, effective principal, reserved `on_behalf_of_id`, source flow|mcp|api|agent|workflow_tool, tool + tool fingerprint, connection, capability, risk/category, frozen policy, argument and action fingerprints, scrubbed preview, lifecycle columns, correlation id) and `approval_rule`; RLS; `SELECT, INSERT` plus lifecycle-column `UPDATE` only (default privileges revoked); trigger enforcing the transition table and freezing security columns and the decider; unique partial index for live actions; `SECURITY DEFINER` scan `grobot_due_pending_actions`.
- **State machine:** PENDING → APPROVED | REJECTED | EXPIRED | CANCELLED; APPROVED → CLAIMED | EXPIRED | CANCELLED; CLAIMED → EXECUTED | FAILED | OUTCOME_UNKNOWN; all else terminal.
- **Binding:** organization, workspace, requester, principal, source and key, tool and tool fingerprint (definition hash; for MCP the approved remote fingerprint), connection, capability, risk, policy fields, arguments. Changing any of them finds no approval.
- **Tool Gateway:** approval gate after authority, declared tools, connection, grant and risk checks. Reuse or create the live action by (source key, fingerprint); `APPROVED` is claimed by one conditional UPDATE right before the normal executor path, then finished EXECUTED/FAILED/OUTCOME_UNKNOWN. Revalidation is the same pipeline. Pre-send failures after a claim are FAILED with `approval.revalidation_failed`.
- **Policy:** built-in floor (HIGH/ALWAYS need approval; CRITICAL blocked; self-approval allowed by default); organization rules by tool, category (FINANCIAL, DELETE, ADMINISTRATIVE, …) or risk can add requirements, `self_approval = different_principal`, a minimum approver role, and decide/execute windows (default 24 h / 1 h). A rule never removes the floor. The rule in force is frozen on the request. Eligibility is computed on the server; refused attempts audited.
- **Flow:** the step parks WAITING (no worker held) with the action id; approve → retry due now; reject/expire/cancel → step fails (`APPROVAL_REJECTED|EXPIRED|CANCELLED`, `on_error: continue` works); ending or cancelling a run cancels its actions; a crash after a claim → `OUTCOME_UNKNOWN`, never retried. The existing workflow `APPROVAL` step is unchanged and stays a separate content target (ADR 0036).
- **MCP:** immediate `approval_required` carrying `{id, status, expires_at, summary, next}`; retry the same call after approval; `grobot_approval_status` (own approvals only); no protocol extension.
- **API:** `GET /action-approvals` (filters: status, risk, tool, requester, workspace, since; keyset paging), `/summary`, `GET /{id}` with audit history, `POST /{id}/decision` (quotes the fingerprint), `POST /{id}/cancel`; `GET/PUT/DELETE /approval-rules` (`approval:configure`, administrators). `/approvals/summary` now `{pending, steps, actions}`. New permission `approval:configure`.
- **Console:** Approvals page with "Actions" and "Workflow steps" tabs and Pending/Approved/Rejected/Expired/All views; detail view (what will happen, account, requester, source with run link, risk, policy sentence, arguments, history); Approve/Reject/Cancel only when the server says allowed, with a reason otherwise; Settings → Approvals rules panel; sidebar badge counts both kinds.
- **Operations:** Celery beat `flow.sweep_approvals` every 15 s (expire overdue, mark abandoned claims OUTCOME_UNKNOWN after 20 min, wake affected runs); outbox events `action_approval.requested|decided|finished` for future notifiers; audit `approval.requested|approved|rejected|expired|cancelled|claimed|execution_started|executed|execution_failed|outcome_unknown|revalidation_failed|decider_refused` and `approval.rule_set|rule_removed`.
- **CI:** required `approvals` job (`make approvals-test`) in the gate.
**Evidence:** full run 5 937 Python tests (Docker tier included), 144 web, 42 widget, 92 end-to-end (89 + 3 new browser scenarios); ruff, mypy, eslint, tsc, prettier, `alembic check` clean; migration round trip verified. New: 68 primitive tests (canonicalization, fingerprint, state machine, policy), 52 gateway/engine tests (binding, tampering, expiry, rejection, cancel, revocation, outcome unknown, concurrency with barriers, separation of duties, tenant isolation, DB trigger refusals, sweeper, audit without secrets), 10 Flow tests, 19 API tests, 6 MCP service tests, 4 import-boundary rules, 7 web unit tests, 3 real-browser scenarios (workflow approve + reject in the console, MCP continuation with real OAuth, different-principal rule). J (crash mid-call → OUTCOME_UNKNOWN, no retry) is covered by the core Flow test.
**Found and fixed during the work:** a stale ORM identity map let a second approver succeed after the first on a locked read (fixed with `populate_existing`; re-run 12×); default table privileges had left the application role full access to `pending_action` (explicit REVOKE); the workflow deadline can arrive before an approval's 24 h window (the run times out and its approvals are cancelled; documented).
**Decisions:** content approval and tool-call approval stay separate targets under one page (ADR 0036); a changed call at the same workflow step supersedes the stale approval while MCP calls with different arguments do not cancel each other; a failure after approval consumes it and a new request needs a new approval; rules can add but never remove the floor.
**Known limitations:** no notification delivery (events exist); approver authority checked at decision time only; no delegation, approver groups or bulk approve; transient failure after approval costs a second approval; `agent`/`workflow_tool` sources are schema-only; search results' `requires_approval` flag still reflects risk, not organization rules.
**Deferred (not M13.1):** unified Tool Registry, scheduled MCP rediscovery, OAuth stale-code/token purge, workflow-as-tool execution, Cortex/LangGraph, notifications.
**Accepted:** tag `m13.1-accepted` = `6c23153`.

### M13.2 — Unified Tool Registry & Risk Administration  ☑ (accepted)
Design: ADR 0037 (the registry describes, the gateway executes), 0038 (risk precedence, floors, who may loosen what), 0039 (scheduled MCP rediscovery, OAuth cleanup); `docs/tool-registry.md`.
**Goal:** one inventory of every callable capability (Native, REST, Webhook, MCP) with search that scales to thousands and never dumps the catalogue into a model context; audited risk overrides (lowering needs a stronger permission than raising); scheduled MCP rediscovery; OAuth cleanup; admin Tools page.
**Built:**
- **Registry** (`grobot_core.toolregistry`): a derived, rebuildable projection (no copy of any source). Static half = deterministic index of the tool definitions (shared, no tenant data, rebuilt when the definitions change); tenant half (connections, grants, MCP tools/drift, overrides, approval rules) read in a handful of queries and evaluated in memory. Entries expose stable id, source, provider, category, support, risk (effective/source/floor/override), approval policy (from M13.1), connection + grant, health, MCP drift (`CURRENT|NEW|CHANGED|REMOVED|UNREACHABLE`), version, and a derived `availability` with reason codes (advisory only; no `executable` flag).
- **Two audiences:** administrative registry (`tool:read`) vs callable discovery (`tool:invoke`: compact, no administrative metadata, hidden = non-existent). The consumer contract `ToolDiscovery` (`search_tools`, `get_tool`, `get_tool_schema`) has no verb that executes.
- **Search:** one deterministic lexical engine (field weights, prefix and curated-synonym matching, word rarity, coverage first, stable ties) shared by the Console and MCP `grobot_search_tools` (whose `requires_approval` now reflects organization rules and overrides). No embeddings.
- **Risk administration:** `effective = max(system floor, override-or-source)`; floor = source HIGH/CRITICAL; raise needs `tool:classify` (admin), lower needs `tool:risk_downgrade` (owner) + a reason, decided by effective before/after; stale lowering lapses; versioned writes; append-only `tool_risk_history`; audit `tool.risk_changed|risk_override_removed|risk_change_refused|reconciled`; the gateway applies the override on the next call and changes nothing else.
- **Scheduled MCP rediscovery** (worker beat, 60 s tick; per-server cadence 15 min, jitter, backoff, lease, caps per tick/org) running the same hardened discovery; new tools inert, changed stopped, removed unavailable; audit/event noise bounded; credential failures now recorded and backed off. **OAuth cleanup** (hourly, bounded, `SKIP LOCKED`, active rows untouched).
- **API:** `/organizations/{org}/workspaces/{ws}/tools` (+ `/facets`, `/drift`, `/discover…`, `/{id}`, `/{id}/schema`, `/{id}/risk` PUT, `/{id}/risk/reset`, `/{id}/risk/history`, `/reconcile`). **Console:** Tools page (filters, search, paging, review banner), tool page (why it can/cannot run, approval policy, drift, inputs, risk form with consequence text, history).
- **Schema** (migration `a9c7e14f3b68`): `tool_risk_override`, `tool_risk_history` (RLS; history insert-only + immutability trigger), rediscovery columns on `mcp_server_state`, two identifier-only `SECURITY DEFINER` scans (`grobot_due_mcp_servers`, `grobot_stale_mcp_oauth`). New permissions `tool:read|classify|risk_downgrade|reconcile`.
- **CI:** required `registry` job (`make registry-test`) in the gate.
**Evidence:** full run 6 122 Python tests (Docker tier included; +185), 150 web (+6), 42 widget, 99 end-to-end (92 + 7 new scenarios A–H on the real stack); ruff, mypy (all 382 files, incl. 22 older test-typing errors fixed), eslint, tsc, prettier, `alembic check` clean; migration round trip (8 revisions) and single head verified. Real pinned catalogue: 774 integrations, 8 051 actions, 7 419 registry entries; rebuild ≈1 s, list 30 ms, filtered 47 ms, search 15 ms, detail 8 ms.
**Decisions:** derived index over a copied table (nothing to reconcile; no per-tenant 7k-row copies); floors are the source classification, so an override can never switch off the approval floor; removing an override that raised a tool is a lowering; reconcile = rebuild the process's index; approver authority at execution deliberately unchanged (recorded as future approval-policy hardening).
**Known limitations:** index is per process (~1 s, 27 MB at 7.4 k entries); overrides are organization-wide; search is lexical; MCP reviewer classification still happens in MCP review.
**Accepted:** tag `m13.2-accepted` = `57ad713`. Final verification on that commit: full Python suite 6 122 passed, 0 failed.
**Carried forward:** approver authority is still checked only at decision time (future approval-policy hardening, not changed here); M13.3 consumes the registry only through `ToolDiscovery` and executes only through the Tool Gateway.

### M13.4 — First production-style agentic workflow  ☑ (accepted)
**Delivered:** see `docs/agent-actions.md`, ADR 0049 (execution identity) and ADR 0050 (conversation → Cortex delegation). Scenario (a deliberate change from the original "Lead Follow-Up Agent from a Flow" sketch, per the M13.4 brief): *website conversation → qualified business action*. A visitor completes a lead (or asks for something to be done) → the published Agent hands the work to its **pinned** Cortex version through the narrow `AgentActionRuntime` → Cortex searches, loads a schema and calls a capability → the Tool Gateway authorizes it → a person approves where policy requires → the customer's system is called exactly once → the result is written back into the conversation. Real production paths throughout (no demo workflow).
**Identity and authority:** the run acts as the Agent's existing **service account** (ADR 0022), workspace-scoped, ceiling-limited, revocable, resolved afresh on every call; the visitor is never a principal. Effective authority = service account ∩ Agent's published allowlist ∩ pinned Cortex tool policy ∩ registry availability ∩ connection/capability grants ∩ Gateway ∩ risk/approval policy; the allowlist is enforced in Cortex and again by the Gateway (`allowed_tools`). Choosing an identity needs `service_principal:use` and a role that already holds its permissions. Publication validates the link (not integration availability).
**Boundary and results:** `AgentActionRuntime.request()` → safe `ActionStatus` (`in_progress`, `waiting_approval`, `completed`, `declined`, `failed`, `cancelled`, `outcome_unknown`, `unavailable`); success is claimed only from a recorded successful call; `OUTCOME_UNKNOWN` is never success and promises no retry; no message names a tool, policy or principal. Results are durable messages written in the same transaction that parks or ends the run (new *parked* hook beside the terminal hook), delivered live by the widget's event stream (now relays agent action updates, `human: false`). Idempotent by request identity (`conv:{conversation}:{trigger}:{hash}`), at most 3 actions per conversation. The approvals API gained `agent_run` (run, agent, conversation, identity).
**Verification (local):** full Python suite 6 443 passed including the Docker tier; `make cortex-test` 181; `make agent-actions-test` (new, 355: unit, chat-runtime, DB tier with the real Gateway/Approval Engine/RLS, API, Agent/Cortex/Flow/lead/hand-off regression); web 163, widget 43; real-stack E2E `e2e/test_agent_actions.py` 6/6 (approval path, unattended path + duplicates, rejection, capability escalation, revocation while an approval waits, no identity) and the whole E2E suite: 115/115 on the previous harness, 115/115 on the final harness, and one further full run with 114/115 (a single Playwright `load` stall in `test_knowledge_ui` after the server had already deleted the knowledge base and served the redirect; it passes in isolation and in the other runs, cause not proven; the USB drive dropped out three times that day); ruff, mypy-strict, eslint, tsc, prettier, `alembic check` clean; migration `d4a1e7b92c30` round-trips one step.
